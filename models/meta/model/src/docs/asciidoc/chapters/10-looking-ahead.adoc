== Looking ahead

=== A text syntax

Meta has a text syntax in the making, for files with the extension `.nmeta`: metamodels written the way Xcore writes Ecore models, parsed by the ANTLR runtime alone, with no Xtext and no Eclipse.
One file is one package:

[source,text]
----
/** Orders placed in the shop. Documentation is Markdown. */
package shop namespace "https://example.org/shop" prefix "shop" version "1.0.0"

import "https://example.org/party" as party
annotation "urn:org.nasdanika" as Nasdanika

type Instant as dateTime wraps java.time.Instant

enum Status { DRAFT, PLACED as "placed" = 1, SHIPPED as "shipped" = 2 }

abstract class Entity { id string code }

@Nasdanika(icon = "bi-cart")
class Order extends Entity {
    Instant placedAt
    Status status = "DRAFT"
    refers party.Customer customer
    contains OrderLine[*] lines opposite order
    derived readonly number total
}

class OrderLine {
    refers Order order opposite lines
    string | number sku
}
----

Documentation comments become Markdown documentation, multiplicities follow the type as in Xcore, `|` and `&` write unions and intersections, and text in backticks is an opaque type.
The grammar is written, in `src/main/grammar/Meta.g4`, and is not part of the build yet; the builder that turns a parse into a package is to be written [.sketch]#SKETCH#.

=== Sources and targets

A vocabulary comes in through surfaces where people author it and harvesters of what is already written down, and goes out through projections [.planned]#PLANNED#:

[cols="1,4",options="header"]
|===
| Direction | Formats
| Authored in | Excel, for the people who already keep the vocabulary there; Draw.io, where the diagram is the source, not a picture of it; Markdown, where the prose matters most; the text syntax; the Groovy DSL, for construction in code
| Harvested from | Ecore, Java, XML Schema, JSON Schema and database metadata. Most of a domain model is already written down somewhere, and asking people to type it again is how modeling efforts die
| Projected to | TypeScript packages with type information at run time; JSON Schema, for validation and for the tool schemas of agents; Ecore, as a dynamic package, and Xcore text for generated Java; documentation sites with diagrams; SQL, Java or Python on demand
|===

=== Flattening

Inheritance is how a model is authored.
It is not always how it is consumed: a TypeScript interface, a JSON Schema for a tool call and a summary handed to an agent all read better as a flat class, with every inherited feature and operation inlined.

Flattening is a transformation from Meta to Meta [.planned]#PLANNED#, not a trick inside each emitter: the input is a package, the output is a package whose classes declare everything they inherited, and every copied feature carries a marker back to the class that declared it.
It is testable by comparison, reusable by every projection, and auditable.

Flattening is also where composition stops being free:

* Most encounters of the same name are not clashes. A feature reached twice through a diamond is one feature, and an operation declared again with the same signature is an override. Deduplicate by identity, not by name.
* The same name with different declarations is a clash, resolved by renaming, deterministically: the most derived declaration keeps the name, and the rename is recorded on the feature.
* Renaming happens in Meta, not downstream, because TypeScript refuses an interface that extends two interfaces declaring a member incompatibly, and a strict tool schema has no room for the composition that would otherwise carry it.

What a cut must not do is erase distinctions: removing an ancestor's name is recoverable by widening the cut, while replacing a class by its ancestor removes a distinction nothing can recover.

=== Situated vocabularies

Classes and features will be situated in coordinates such as jurisdiction, language, tier and audience [.planned]#PLANNED#.
One vocabulary then carries its variants together, the features that differ marked by the coordinates they apply in, and generating for a coordinate emits what applies there and nothing else: a product line, not a fork.
Meta's annotations already carry such facets as data.

=== Kinds and types

A type, a Meta class or an Xcore class, fixes structure: which features an element has.
The runtime's core model is gaining kinds, which say what an element is for regardless of its type.
Generated Meta documentation will explain the difference, and the kind model comes first [.planned]#PLANNED#.
