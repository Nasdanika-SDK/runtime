== Creating and changing diagrams

A program that writes diagrams puts what it knows where people look.
It can generate a diagram from scratch, from a system, an inventory or a model, or change one that people drew, to mark what a check found or what a deployment did, and leave the rest of the drawing as it was.

=== Creating a diagram

A new document has no pages; a new page has a model, a root and one layer.
Nodes are created in a layer, or in another node:

<2> The default layer. `root.createLayer()` adds another.

A node created by the API gets a generated ID; `setId` replaces it with a readable one.
Its geometry is relative to its parent: to the page for a node in a layer, to the containing node otherwise.

=== Styles

An element's style is the `style` attribute in the file, a list of `key=value;` pairs, and `getStyle()` returns it as a live `Map<String, String>`.
Changing the map changes the attribute.
`Style`, `LineStyle`, `NodeStyle` and `ConnectionStyle` add typed, fluent methods for common keys on top of the map:

* `Style`: `opacity`, `rounded`, `shadow`, `enumerate` and `enumerateValue`;
* `LineStyle`: `color`, the stroke, `width` and `dashed`;
* `NodeStyle`: `backgroundColor`, the fill, `shape`, `align`, `verticalAlign`, `fontSize`, `fontColor`, `fontStyle`, `labelBackgroundColor`, `labelBorderColor`, `rotation`, `container` and `collapsible`;
* `ConnectionStyle`: `edgeStyle`, `startArrow`, `endArrow`, `startFill`, `endFill` and `jump`, with the `Arrow` and `Jump` enums for the common values.

The typed methods are a convenience, not a complete list.
Draw.io has hundreds of style keys, and any of them can be put into the map directly: `style.put("gradientColor", "#7EA6E0")`.
The easiest way to find the key for an effect is to apply it in Draw.io and look at _Edit Style_.

=== Changing a diagram that people drew

The most useful writes are often small.
A program that knows something about the elements of a diagram can show it on the diagram, and leave the layout, the wording and everything else that people decided alone.
Nasdanika core called this representation filtering: the source diagram stays as it is, and the diagram people see shows the current state of affairs.
Systems under maintenance turn translucent, systems with an incident get a red border, planned systems are gray, and readers grasp the state of a landscape at a glance.

`NodeImpl.onRemove()` calls `clear()` on `getAllIncomingConnections()` and `getAllOutgoingConnections()`, which looks intended to remove the node's connections with it. The lists are copies, so `clear()` has no effect, and `remove()` leaves dangling connections, as the listing above shows.
