== The rest of the continuum

This module covers the middle of the continuum: a diagram as data, read, checked, changed and written by programs, and shared as an interactive page.
The points to its right exist in Nasdanika core, built on its graph, mapping and HTML application modules.
In the runtime they will be rebuilt on its own foundation, and this chapter says how, as far as it is designed.
Everything in it is [.planned]#PLANNED# unless it says otherwise.

=== Documented diagrams

A documentation site generated from a diagram: a page per documented element, a navigation tree from the diagram's containment and links, the diagrams embedded in the viewer and linked to the pages, and search.
In Nasdanika core, the `drawio html-app site` command of the Nasdanika CLI, and a GitHub template repository that runs it, generate such sites, from documentation in properties, from Markdown files that elements refer to, and from prototypes that mount other sites.

In the runtime, sites will be generated with its HTML and Bootstrap modules, which its own site is planned to be generated with as well.
The diagram supplies the tree, the element properties supply the pages, and the API of this book reads both.

=== Executable diagrams

Behavior bound to diagram elements: a property names the code an element stands for, and the code is wired to its neighbors along the diagram's connections.
Nasdanika core does this with graph processors, which exchange handlers and endpoints along connections, synchronously or concurrently, and are created from invocable URIs in element properties.

The design for the runtime is open.
Its natural foundation is the runtime's capability framework, which finds and creates the code that a requirement names, with the diagram as the wiring, and its telemetry, which would record what the diagram did.

=== Diagrams as models

Diagram elements mapped to the objects of a typed model, so that a diagram is one of the sources of a model alongside spreadsheets, scripts and code.
In Nasdanika core, semantic mapping does this: element properties name the classes and features of an Ecore metamodel, and a diagram loaded into a resource set is a model.

The runtime takes a different road there, and the first part of it is built, in modules beside this one [.available]#AVAILABLE#:

* *The Draw.io model*, `models/drawio`, is an EMF model of Draw.io documents. A `.drawio` file, or a PNG or SVG image that Draw.io exported with the diagram in it, loads into any resource set of the runtime as a model, through a resource factory that the module contributes, and saves back. It reads and writes with the API of this book. Its Zephyr Book is _Draw.io Model_.
* *The diagram model*, `models/diagram`, which the Draw.io model extends, gives every element semantic elements: references to the objects of other models that the element depicts. Its Zephyr Book, _Diagram Model_, maps the figure of its own metamodel, drawn in Draw.io, to that metamodel and checks one against the other.

What remains [.planned]#PLANNED# is the mapping itself without code: element properties that name classes and features, as in core, so that a diagram loaded into a resource set is a model of the domain and not only of the diagram.
Until then, a mapping is a few lines of Java over the diagram model, or a Groovy script: the runtime's Groovy DSL can read a Draw.io resource while it builds a model.

=== One diagram model, many pictures

Most of this is built [.available]#AVAILABLE#.
The runtime's diagram model holds what notations have in common: nodes, ports, connections, layers, nesting and labels, independent of any editor.
A Draw.io document is one: its pages are slides of the presentation model, and slides are diagrams.

* *Layout*, with Eclipse ELK, is written once for the diagram model, in `models/diagram/elk`, and lays out Draw.io pages because they are diagrams. The _Draw.io Model_ book generates a diagram of the modules of a running JVM, lays it out with ELK and renders it with Draw.io's viewer (<<rendering>>).
* *Rendering* goes to React Flow, where a diagram should be interactive, to Draw.io's own viewer, where a diagram should look exactly as drawn, and to SVG, through the runtime's SVG model, where it should be vector graphics in a document. The Zephyr Books _Diagram Layout with ELK_ and _SVG Model_ show them.

[.planned]#PLANNED#: routes in from other notations. The presentation model, for slides, is a sketch, and models of Visio, PowerPoint and Excel files are postponed.

The same path makes diagrams scenes of narrated videos: a diagram on screen, with elements highlighted as a narration mentions them, regenerated when the diagram changes [.planned]#PLANNED#.

=== Rendering generated diagrams

Rendering is built: <<rendering>> renders pages with Draw.io's own viewer, as PNG and SVG images with the page embedded and as videos.
What remains [.planned]#PLANNED# is an Asciidoctor extension that renders a `.drawio` file referenced from a book as the book is built, so that the source of a figure in Git is the diagram rather than its image, and the viewer shipped as a resource, so that rendering does not need the network.

=== Diagrams and AI assistants

A diagram as data is good context for an assistant: a graph of short texts, labels, tooltips and properties, joined by containment, connections and links.
An assistant that is given the elements near the one a person asks about, by graph distance as well as by similarity of text, answers questions about an architecture more precisely than one given the whole diagram as an image.
The API of this book is enough to build that context today; the runtime's plans for assistants will build it in.
