`CommandBase` runs `execute` in a span named after the command, with the command's qualified name, class, module and module version as attributes, and hands it the span and the logger and meter of the current OpenTelemetry instance.
It also closes the command's sub-commands and mix-ins that implement `Closeable` when it is closed.
`CommandGroup` is a command that does nothing itself: run alone, it fails with "Missing required subcommand", which picocli reports with the usage help.

=== Factories

A command is contributed by a factory:

.A command's factory
[source,java]
----
include::{booktests}/PipelineTests.java[tag=factory,indent=0]
----
<1> The command's class, whose declarations decide where it goes.
<2> Creating the command, once it is known to go under a parent. A publisher, so a factory can create several commands, or none, or create them later.

`SubCommandCapabilityFactory` does the rest.
For each place in the tree it is asked about, it checks whether the command goes there (<<wiring>>), creates it with `doCreateCommand`, wraps it in a picocli `CommandLine`, and asks, in the same resolution, for the command's own sub-commands and mix-ins.

A factory that decides in code overrides `match(parentPath)`, which sees the whole path from the root, or `createCommand`, which is called for every place and creates the command where it should be.
The runtime's root command factory does that: it creates the root where the path is empty.

=== Limits

A command that takes any parent, or a pair of commands that take each other, would grow the tree forever.
Two limits stop it, with a warning in the log:

* a parent path of at most 15 commands, set with the system property `org.nasdanika.sdk.runtime.cli.maxCommandPath`;
* at most 2,000 commands in a tree, set with `org.nasdanika.sdk.runtime.cli.maxCommands`.

A factory can also refuse places by itself: the runtime's `ecore` command, which filters what its parent supplies and supplies the result, refuses to go under another filter, which would otherwise nest without end.
