[#models]
== Models: EMF without Eclipse

Everything the runtime defines is a model, and every model is EMF.
This chapter explains what EMF gives you, why it no longer needs Eclipse, and how a model goes from a text file to generated Java, registered with resource sets, saved in any of six formats and loaded from a module.
The example is the library model that the rest of the book uses as its domain.

=== Why EMF

A model is a typed graph.
Its nodes are objects of classes, and its edges are references, some of which are containment: a library contains its books, a book refers to its authors.
The classes, their attributes and their references are themselves described by a model, the metamodel, and EMF's metamodel of metamodels is called Ecore.

That sounds abstract until you list what a typed graph buys once a framework handles it for you, which EMF has done for more than twenty years:

* *Reflection.* Any object can be asked for its class, and any feature can be read and written by name, without generated code. A viewer, a serializer, a query engine or a diff tool written once works for every model.
* *Serialization.* XMI, and with the runtime JSON, YAML and two binary formats, all lossless and all reflective.
* *Resources and URIs.* Objects live in resources identified by URIs, and resources live in resource sets. A reference from one resource to another is a URI that is resolved lazily, when it is followed, which is what lets models reference each other across files, repositories and the network.
* *Integrity.* Containment means one owner. Opposite references are maintained in both directions. Multiplicities are declared and checked.
* *Notifications and change recording.* Every change to an object is a notification, and a change recorder can capture a set of changes as a model of its own, which <<telemetry-model>> turns into an audit trail.
* *Operations.* Classes declare operations, and with operation reflection an operation can be invoked by name with a list of arguments.

The last item matters more every year.
An operation with a name, typed parameters and documentation is a tool, in exactly the sense an AI agent or a command line needs.
Defining an API as model operations means it is documented, invocable and discoverable by construction.

=== Why not Eclipse

For most of its life, EMF lived inside the Eclipse IDE.
To define a model you installed Eclipse with the modeling tools, created a workspace and a plug-in project, drew or typed an Ecore model, and generated code with a wizard that wrote `plugin.xml`, `MANIFEST.MF` and a generator model next to it.
The output was an OSGi bundle meant to run inside Eclipse.

None of that is EMF.
EMF core is a set of plain jars on Maven Central, and the runtime uses them as plain jars: named JPMS modules on the module path, with no OSGi, no workspace and no plug-in registry.
The modeling tools were the problem, and two things replaced them:

* *Xcore*, a text syntax for Ecore models with operation bodies, which reads like a small programming language and diffs like code.
* *The Xtext Maven plugin*, which generates Java from Xcore in any Maven build, on any machine, in CI, and in editors that are not Eclipse.

So a model is a source file in a Maven module, generated by the build, and committed with the code.
I described the journey of getting there in "The Architectural Stalker", about liberating useful artifacts from the Eclipse zone; this chapter is the result.

=== Ecore in one page

[cols="2,3,3",options="header"]
|===
| Concept | Ecore | In the library model
| A namespace for related types | `EPackage`, with a namespace URI and a prefix | `library`, `https://example.org/library`
| A type of object | `EClass`, possibly abstract, with supertypes | `Library`, `Author`, `Book`
| A value-typed property | `EAttribute`, typed by an `EDataType` | `Book.year`, an `int`
| A link to other objects | `EReference`: containment or cross reference, single or many, with an optional opposite | `Library.books` (containment), `Book.authors` (cross reference, opposite `Author.books`)
| A fixed set of values | `EEnum` with literals | `Genre`
| Behavior | `EOperation` with parameters | `Library.publishedBefore(int)`
| An instance | `EObject` | a particular book
| A unit of storage | `Resource`, identified by a URI | `shelf.library`
| A working set of resources | `ResourceSet`, which resolves URIs between them | the resource set a command creates
|===

A few things in the header are worth understanding, because they are where most first attempts go wrong.

`@Ecore` gives the package its namespace URI and prefix.
The namespace URI is the package's identity: it is how serialized instances name their classes, how a resource set finds the package, and, by the runtime's identity rule, where the model's documentation page lives.

`@GenModel` configures the code generator:

* `modelDirectory` says where generated Java goes, and its first segment must be the name of the Maven module's directory: `/library/src-gen` for a module in `library/`. The generator resolves that segment as an Eclipse project name, and under Maven a mismatch produces a successful build with no generated code at all. If `src-gen` comes up empty, look here first.
* `+complianceLevel="25"+` lets the generated code use the Java version the runtime targets.
* `+featureDelegation="Dynamic"+` makes generated getters and setters go through EMF's dynamic feature storage, which keeps generated classes small and lets a base class intercept feature access.
* `+operationReflection="true"+` generates `eInvoke`, so that operations can be called by name.

The `import` brings in `NamedElement` from the core model, which is resolved from the module's compile class path when the model is generated.
Comments in `/* */` before a class or feature become its documentation in the generated model.
Operation bodies are written in Xbase, a Java-like expression language; the body of `publishedBefore` compiles to the loop you would expect.

=== Resource sets configured from services

`NasdanikaResourceSet.createAndConfigure()` is the line that connects EMF to everything on the module path.
It creates a resource set and configures it from four kinds of services:

* *URI handlers* (`URIHandler`), added in front of EMF's own, so a module can teach every resource set a new URI scheme.
* *Adapter factories* (`AdapterFactory`).
* *Packages* (`EPackage`), registered by namespace URI.
* *Contributors* (`ResourceSetContributor`), which may do anything else with the resource set, typically register resource factories.

Configuration runs in a `ResourceSetContributor.configure` span with a log record per contribution, and then wraps every URI handler, the default one included, in a `TelemetryURIHandler`, so that every stream a resource set opens is a span with a byte count and progress records.
That is why the first program in <<getting-started>> was observable without trying.

Three variants of `createAndConfigure` exist for when the defaults do not fit.
One takes a `ClassLoader`, for code that is not on the module path, such as plugins loaded at run time.
One takes an `OpenTelemetry` instance and attaches it to the resource set, so that work done outside any unit of work, proxy resolution much later for example, still reports somewhere.
And one takes both.

`NasdanikaResourceSet` also supports global objects: `registerGlobal(uri, object)` makes an object resolvable by a URI that no resource contains, which is how a catalog of shared elements is offered to every model that references it.

Which one to use is a question of who reads the file.
XMI is the interchange format every EMF tool understands, and it diffs reasonably.
YAML is the one people edit and review.
JSON is the one a browser or a JavaScript program consumes, and <<web>> shows where that leads.
The binary formats are for size and speed, such as telemetry from a long run or a snapshot of a large system.

=== Loading from modules

Two URI schemes contributed by `common` load resources from the code itself:

* `classpath://path/to/resource` reads through the context class loader.
* `module://module.name/path/to/resource` reads from a named module.

The library module ships a small catalog at the root of its jar, and the test loads it by the module's name:

.Loading a resource from a module
[source,java]
----

JPMS encapsulation applies here.
A resource in a directory that corresponds to one of the module's packages is visible to other modules only if that package is open; a resource outside any package, such as at the root of the module or under `META-INF`, is always visible.
Put resources meant to be loaded by URI outside the package directories, or open the package they are in.

=== What you have now

A model is a text file in a Maven module.
The build generates its Java; a service registers it with every resource set; a contributor adds whatever else the model needs; and the model is saved and loaded in the format each reader prefers.
No IDE was involved.
