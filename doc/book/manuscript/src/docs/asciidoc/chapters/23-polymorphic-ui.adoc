[#polymorphic-ui]
== Polymorphic UI

A model with fifty classes should not need fifty screens.
A polymorphic user interface renders each element with the view of its class, the way a method call dispatches on the class of its receiver.
The benefit is the same as for methods: the general case is written once, and the specific cases only where they earn their place.

This chapter builds one from pieces the runtime already has: the capability framework finds the views, the class hierarchy of the model orders them, and the HTML and Bootstrap models of <<web>> are what they produce.

=== Where the idea comes from

The idea is old, and its history is the best argument for it.

*JFace.* An Eclipse tree or table viewer does not know what it displays.
A content provider tells it the children of an element; a label provider tells it the text and the icon.
One viewer shows anything for which those two can answer.

*EMF.Edit.* For every class of a model, EMF generates an item provider that is both the content and the label provider of its instances, along with a property source for the property sheet.
Adapter factories find the item provider of an object's class, and a reflective item provider answers for classes without one.
That is how a tree editor, generated in minutes, edits any Ecore model.

*Naked Objects.* Richard Pawson argued in the early 2000s that a user interface should be generated by reflection over the domain object model, and that a domain model from which no decent interface can be generated is probably the problem.
I saw it presented at a conference at the time, and the idea stayed with me.
It lives on as Apache Causeway, and the reflective interface has been rediscovered roughly once per platform generation since: Django's admin, JSON Forms, the metadata-driven screens of the large business platforms.

Three things are different here:

* *The model is the source, and code is one of its outputs.* Naked Objects derives the model from the classes; here the classes, the documentation, the schemas and the user interface all come from the model.
* *Views are contributions.* A module adds views by declaring them, and the capability framework finds them, the way EMF.Edit finds item providers through adapter factories, with no registry to maintain.
* *The output is a page model*, rendered to static HTML or to React components that run in a browser with no JVM behind them (<<web>>).

=== Dispatch on the class of an element

Method dispatch looks for the most specific implementation along a class hierarchy.
A model's class hierarchy is explicit and reflective, and it has multiple inheritance: a library's `Book` extends the core model's `NamedElement`, which extends `ModelElement`, which mixes in identity, documentation and provenance.

<1> Only the requirement for this exact class. A view of `NamedElement` does not answer for `Book`; the resolver asks for `NamedElement` itself when `Book` has no view.
<2> The factory is its own capability.

Asking for exact classes is deliberate.
A requirement matching every superclass at once, such as the generic type `Function<? super Book, Node>`, would leave the choice between the matching views to the order in which capabilities are returned, and that order compares erased types, as the editor's note of <<generic-types>> explains.
With one class per requirement, the first answer along the lineage is the most specific view, by construction.

=== Mix-ins and sections

Because the lineage walks every superclass, a view can be contributed for a mix-in.
A view of `Documented` renders the documentation of anything documented that has no nearer view; a view of `Marked` renders provenance.

The resolver above stops at the first view, which suits a card or a row.
A page can instead collect a view from every level of the lineage, nearest first: the fields of the class itself, then the documentation section contributed for `Documented`, then the provenance section for `Marked`.
Each class and each mix-in contributes what it knows, and a new mix-in brings its section to every page of every class that uses it.
This is multiple inheritance applied to user interfaces, and it is a small change to the resolver: ask for all the views at each level instead of the first one.

=== Static pages, and the browser

The pages in this chapter are static HTML, generated once and served by anything.
The same views can render inside React components: an `Intrinsic` places an element of the HTML model in a component, and `JsxContent` places JSX inside an HTML element, so the page model of a view becomes part of an application that runs in a browser (<<web>>).

Every resolution is a capability resolution, so it is traced: the telemetry of a page generation says which view rendered which element.

=== What comes next

The pieces of this chapter are available in the runtime; the example assembles them.
The roadmap turns them into a product [.planned]#PLANNED#:

* *The reflective viewer.* A browser application that renders any model this way: a property sheet for every object, with categories from the annotations Xcore models already carry, and views resolved by class through the capability framework.
* *Telemetry and JVM browsing*, with the generic views first and specific views, such as a timeline for spans, where the generic ones are visibly weak.
* *Documentation sites*, where every element of every model gets a page assembled from the views and sections along its lineage, and from its micro-wiki (<<core-model>>).
