[#telemetry]
== Telemetry in the runtime

Telemetry usually arrives late in a project.
The code works, it goes to production, something misbehaves, and somebody adds logging, then tracing, then a vendor's agent that instruments what it can guess at.
By then the code was written without the question "how will anyone know what this did?", and it shows.

In the runtime, telemetry is part of the code from the first line, and the first program in <<getting-started>> showed what that buys: a program with no telemetry code of its own was observable, because everything it called reported what it did.
This chapter explains the conventions behind that, how to instrument your own code the same way, and where the telemetry goes.

=== Two kinds of telemetry

Mainstream observability is built for the firehose.
It collects everything cheaply, samples, keeps it for days or weeks, and answers "is it healthy right now?".
That is the right tool for operations, and the runtime does not compete with it.

There is another kind, which most organizations do not have at all: telemetry that is collected deliberately, kept indefinitely, and resolved against models of the systems and the work, so that years later it can answer "who changed what, in the course of what work?".
I call it strategic telemetry, and its rule is that every signal is precious.
It is cheap at the scale it operates on, and what is expensive is not being able to answer.

Both kinds start from the same instrumentation.
Code reports through the OpenTelemetry API, and whoever runs the code decides whether the signals go to an operational backend, to a console, into a model that is kept forever, or to all three.

=== The conventions

Four conventions make the runtime's telemetry consistent.
They were stated in <<principles>>; here is what each means in code.

*Spans for operations, log records for what happens in them.*
An operation that has a duration is a span: loading a resource, resolving a requirement, executing a command.
Everything that happens within an operation is a log record emitted through the OpenTelemetry Logs API and correlated with the current span: a message, a warning, a measurement, progress.
Span events, `Span.addEvent`, are not used, because OpenTelemetry is moving events onto the Logs API, where an event is a log record with an event name.

*One OpenTelemetry per unit of work.*
A command, a request and a test are units of work.
Each builds or is handed its own `OpenTelemetry` instance and makes it current, the way it would make a span current.
Instrumented code gets the instance from the context, never from `GlobalOpenTelemetry`, which the runtime does not use.
Two commands running in one JVM can therefore send their telemetry to different places, and a test can capture exactly the telemetry of the code it tests.

*The context carries everything.*
The current instance travels in the OpenTelemetry `Context` next to the current span, so it crosses threads wherever the context does: the pump propagates it to its tasks, and content written on another thread runs in the context of the code that asked for it.

*Watching is subscribing.*
A console, a progress bar, a test or a browser watching a unit of work subscribes to the same spans and log records an exporter receives, through a publishing wrapper (<<watching>>).

=== The Telemetry class

`org.nasdanika.sdk.runtime.common.telemetry.Telemetry` is where instrumented code gets its instance, and where the runtime's attribute keys and event names are defined.

[cols="2,3",options="header"]
|===
| Member | Purpose
| `current()` | The instance in the current context, or the no-op instance
| `makeCurrent(openTelemetry)`, `with(context, openTelemetry)` | Make an instance current, as a scope to close
| `of(notifier)` | The current instance, or the one attached to a resource set, for EMF code that runs outside a unit of work
| `attach(resourceSet, openTelemetry)` | Attach an instance to a resource set
| `tracer`, `logger`, `meter` | The runtime's tracer, logger and meter of an instance
| `inSpan(tracer, name, attributes, body)` | Run a body in a new current span; a failure is recorded on the span and rethrown
| `log(logger, severity, eventName, body, attributes)` | Emit a log record in the current context, if the logger is enabled for the severity
| `recordFailure(span, failure)` | Record an exception and set the error status
| `w3cPropagators()`, `extract`, `extractFromEnvironment` | Continue a trace started by another process
|===

The keys and event names are listed in <<telemetry-reference>>.

It prints:

[source,text]
----
+ Catalog books {library.books=3}
  + Catalog a book {library.book.title=Domain-Driven Design}
  - Catalog a book (0 ms)
  [1/3] Processed 1 of 3
  + Catalog a book {library.book.title= }
    ! a book needs a title
  - Catalog a book (0 ms)
  WARN Skipped: a book needs a title
  [2/3] Processed 2 of 3
  + Catalog a book {library.book.title=Design Patterns}
  - Catalog a book (0 ms)
  [3/3] Processed 3 of 3
- Catalog books (5 ms)
----

In a real assembly the unit of work is created once, in one place.
The launcher creates one per command, with an OpenTelemetry SDK whose exporters save the telemetry as models (<<distributions>>).
The HTTP handler creates one per request (<<serving>>).
A test creates one per test, usually a publishing wrapper with deterministic delivery, so that it can assert on what the code reported.

=== What the runtime instruments

Most of the telemetry of a typical program comes from the runtime itself.

[cols="2,3",options="header"]
|===
| Spans | Produced by
| `ResourceSetContributor.configure`, with a log record per contribution | Configuring a resource set from services
| `Contribute To Resource Set` | Each contributor that uses the interface's default
| `Resource.load`, `Resource.save`, `Resource.unload`, with URI, bytes and root objects | Every resource the runtime's factories create, and yours if you use `ResourceTelemetry`
| `URIHandler.read`, `URIHandler.write`, `URIHandler.delete`, with progress every second | Every stream a configured resource set opens
| `Content.writeTo`, `Content.pipe`, and client spans named after the HTTP method | Transfers of volume content (<<volumes>>)
| Server spans named `<method> <route>` | Requests through the volume HTTP handlers (<<serving>>)
| `Transformer.transform`, `Transformer.create` | Transformations (<<flows>>)
| `CapabilityLoader.loadAll`, `CapabilityLoader.loadOne`, `CapabilityFactory.create`, `CapabilityFactory.method`, `Create Capability` | Capability resolution (<<capabilities>>)
| One span per executed command, named after the command | The command line (<<commands>>)
| `Evaluating script`, `Loading <Type>`, `Setting <feature>`, with script line numbers | The Groovy DSL (<<groovy-dsl>>)
|===

=== Crossing threads and processes

Within a JVM, the OpenTelemetry context lives in a thread local, and the runtime carries it wherever work moves.
A pump task runs in the context that was current when it was enqueued.
A stage tracked or awaited on a pump completes in the caller's context.
Content produced by a writer on a virtual thread runs the writer in the context of the reader that started it.
Spans therefore nest the way the work nests, whichever thread does it, and the unit of work's instance travels along.

Across processes, context travels in W3C trace context headers.
`Telemetry.w3cPropagators()` returns the propagators for W3C trace context and baggage; an instance built with them injects `traceparent` into the requests the volume HTTP client makes, and the volume HTTP handler extracts it, so one trace spans both sides (<<serving>>).

A process can also be invoked by something that has a trace of its own: a build step, a function call, a workflow engine.
The runtime continues it from a map of carrier values, such as request parameters, or from the environment variables `TRACEPARENT`, `TRACESTATE` and `BAGGAGE`:

=== Where telemetry goes

Instrumented code never decides, which is the point.
The options are the unit of work's:

* *Nowhere.* With no instance current, `Telemetry.current()` is the no-op instance, and instrumentation costs almost nothing.
* *To subscribers.* A `PublishingOpenTelemetry` wrapper publishes spans and log records as they happen, with or without an SDK behind it (<<watching>>).
* *To an operational backend.* An OpenTelemetry SDK with an OTLP exporter sends everything to a collector, as any OpenTelemetry application would.
* *Into models.* An SDK with the runtime's model exporters saves traces, logs and metrics as EMF resources, next to the models they describe (<<telemetry-model>>).

These combine.
A launcher can export to a backend and to models at once, and still publish to a console.
