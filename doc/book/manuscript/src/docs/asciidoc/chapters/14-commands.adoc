[#commands]
== Commands as capabilities

The command line is the runtime's first user interface, for people, for build steps and for agents.
An agent that can run a command and read a file can use everything the command line offers, with no protocol to implement.

Three decisions shape it:

* *Commands are contributed.* A module that adds a command declares a factory in its module descriptor. Nothing lists all the commands: the command tree is whatever the module path contributes.
* *The tree is resolved.* Commands find their parents and their sub-commands by capability resolution (<<capabilities>>), matched by the generic types they declare (<<wiring>>).
* *A command execution is a unit of work.* Every command runs in a span, and the launcher saves the telemetry of each launch as models (<<distributions>>).

=== Picocli

The commands are https://picocli.info[picocli] commands: annotated classes with options, parameters, mix-ins, generated help and completion.
Picocli is mature, small and dependency-free, and a picocli command is a plain object that the runtime can create, inspect and wire.

The runtime bundles picocli in its own module, `org.nasdanika.sdk.runtime.picocli`, until a picocli release includes the changes the runtime contributed.
Commands import `picocli.CommandLine` as usual.

=== How the tree is built

The command tree is built by resolving one requirement: a `CommandLine` with a `SubCommandRequirement` payload whose parent path is empty.
The runtime's `RootCommandFactory` answers it with the root command, `nsd`.

Every factory that creates a command then asks for the command's own sub-commands, with the command appended to the parent path, and for its mix-ins.
The tree grows within the same resolution until no factory matches a new parent path.
Two limits stop a runaway contribution: a parent path of at most 15 commands and at most 2,000 commands in a tree, set with the system properties `org.nasdanika.sdk.runtime.cli.maxCommandPath` and `org.nasdanika.sdk.runtime.cli.maxCommands`.

=== Groups

A group is a command that does nothing itself.
It organizes sub-commands under a name and gives them something to work on, from its options.

.A group (`cli/.../LibraryCommand.java`)
[source,java]
----
include::{examplesdir}/cli/src/main/java/org/example/cli/LibraryCommand.java[tag=library,indent=0]
----
<1> The group's option, parsed before any of its sub-commands run.
<2> What the group gives: a library, produced when a sub-command asks for it. The generic return type is the declaration that commands match.
<3> The same library as a list of objects, for commands that work on any model.
<4> Loading through a configured resource set, so the file can be in any format the runtime reads.

`CommandGroup` fails with "Missing required subcommand" when it is run alone, which picocli reports with the usage help.
`nsd library --file shelf.yml books` parses `--file` for the group and runs `books`, which asks the group for its library.

A mix-in is added to a command when the command's `@MixIns` annotation lists a supertype of the mix-in, or when the mix-in takes the command through a `@Parent` member.
The `books` command of <<wiring>> asks for `LimitMixIn` and finds it among its mix-ins at execution, so `nsd library books --limit 2` prints two books.

The runtime's mix-ins add common options without a factory, as picocli `@Mixin` fields:

[cols="1,3",options="header"]
|===
| Mix-in | Options
| `ResourceSetMixIn` | `--extension-resource-factory`, `--protocol-resource-factory` and `--content-type-resource-factory`, which map an extension, a protocol or a content type to a resource factory class, and `createResourceSet()`
| `PropertiesMixIn` | `-p` for one property and `-P` for a properties resource, in YAML, JSON or properties format, loaded in order
|===

=== Overriding

Several modules may contribute a command with the same name under the same parent.
The runtime keeps one when it can tell which one overrides the others:

* A command whose class is annotated with `@Overrides` overrides commands of the listed types.
* A command implementing `Overrider` decides, for each other command, whether it overrides it.
* A command whose class is a subclass of another command's class overrides it.

Commands that do not override each other are all kept, and picocli reports the duplicate name.
The same rules apply to mix-ins with the same name.

=== Commands in the runtime

[cols="1,3",options="header"]
|===
| Command | What it does
| `nsd` | The root command, with version information from the module descriptors
| `launcher` | Generates a Java command line, or an options file, from directories of modules and jars (<<distributions>>)
| `save` | Saves its parent's model contents to a file, in any format the runtime writes (<<wiring>>)
| `ecore` | A group that narrows its parent's objects to Ecore model elements
| `shell` | Added by the launcher: an interactive shell over the root command, with `exit`
|===

=== Commands and telemetry

Each executed command is a span named after the command, a child of the launcher's root span.
Spans the command starts, resource loads and saves, capability resolution, content transfers, are its children, and log records it emits are in it.

A parent's work done for a child, loading the library in the example, runs in the child's span when the child asks for it through an `ExecutionSupplier`, so the cost is attributed to the command that needed it (<<wiring>>).
The launcher saves all of it as models in a directory per launch (<<distributions>>), which makes every command run an inspectable record.
