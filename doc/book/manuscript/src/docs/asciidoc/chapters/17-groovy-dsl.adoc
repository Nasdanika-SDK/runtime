[#groovy-dsl]
== Authoring models with the Groovy DSL

XMI, JSON and YAML are good formats for saving models and poor ones for writing them.
Xcore is the language for metamodels (<<models>>), and there is no equivalent for instances: a library, an architecture, a backlog.

The runtime's `groovy` module fills the gap with a Groovy DSL that is driven by the metamodel.
Nothing in it is written for a particular class or feature: every keyword, every nesting and every attribute is read reflectively from the packages the DSL is bound to.
Bind it to a different metamodel and you get a different DSL, for free.

Groovy brings what a home-made language would have to build: nesting, variables, loops, string interpolation, and code where code is the clearest way to say something.

=== The rules of the language

*Entry points.* At the top level, every concrete class of the bound packages whose uncapitalized simple name is unambiguous is a keyword: `library`, `ePackage`.

*Dispatch.* Inside a builder closure, a call whose name is a feature of the current object sets the feature; otherwise a call whose name is a class creates an object of that class in the one containment feature that accepts it.
When a class fits more than one containment feature, or the feature is typed by an abstract class, the feature is named and the class given explicitly: `eStructuralFeatures('EReference') { ... }`.

*Built-in keywords.* `ref`, `dsl`, `onSave`, `loadResource`, `copy` and `eObject` at the top level, and `global`, `proxy`, `loadResource`, `copy` and `eObject` in a closure, win over both kinds of dispatch.

*Setting features.* `year 2003`, `year(2003)` and `year = 2003` all set the feature.
One form is a trap: `upperBound -1` is the expression `upperBound - 1` in Groovy, which reads the feature, subtracts one and discards the result.
Whenever a value starts with a minus or a plus sign, use the assignment or the parenthesized form.

*References* take one of three values:

* An object the script holds, in a variable.
* A path in the style of EMF URI fragments, resolved after the script has run: `/` anchors it at the root, `..` goes to the container, and predicates select by attribute, as in `+../books[name='Patterns of Enterprise Application Architecture']+`. A path containing `#` is a URI, resolved against the script's own URI, possibly in another resource.
* A closure, evaluated after the script with the referencing object as its delegate, which returns an object or a path.

*Names of classes* can be simple (`Book`), uncapitalized (`book`), qualified by a package path (`library.Book`) or a namespace URI with a fragment (`<nsURI>#Book`).
When a simple name matches several classes and one is a subclass of another, the more specific class wins, which is what makes refinements of a metamodel work in the same script as the metamodel itself.
A name that is still ambiguous is an error that lists the qualified alternatives.

*Results.* The contents of the resource are the script's last expression, if it is an object or a collection of objects, and otherwise the roots created by entry points.

=== Scripts that derive models

A script is not limited to transcribing a model:

* `loadResource 'payments.drawio'` loads another resource through the script's resource set, relative to the script, with every handler and factory the set has. A script can iterate a diagram, a spreadsheet or another model and emit a model from it, which turns a transcription into a derivation.
* `copy '<uri>#<fragment>' { ... }` deep-copies an element as a prototype and then populates the copy like a new element: structure from a diagram, details from code. A copy is a snapshot, not a live link.
* `global '<uri>'` registers the current element under a URI, so that other resources in the same resource set can reference it.

A DSL resource is read-only by default, because the script, not the model, is the source of truth and there is no general way to write a model back as a script.
An `onSave` callback in the script decides what saving means when it should mean something: writing the model elsewhere, or rewriting the script.

=== What comes next

The DSL is built on the JDK's scripting API, `javax.script`, so the same pipeline can serve other JVM languages [.sketch]#SKETCH#.
Kotlin scripts are designed, with the same qualifiers, so `reading-group.library.kts` would load like the Groovy script.
Validation rules expressed in the DSL, and a path from a sketched metamodel script to Xcore and generated code, are part of the same design.
