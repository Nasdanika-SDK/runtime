[#web]
== From models to the web

A model that the people who own it cannot read is a private notation.
The web is where they read, so the runtime treats web pages and web applications as generation targets, and generates them the way it does everything else: from models, into models, and only then into text.

=== Pages are models too

Generating HTML by concatenating strings is easy to start and hard to keep correct: escaping, nesting, attribute order, the one closing tag that went missing.
The runtime's generators build a model of the page and let a generator write the text.

[cols="1,3",options="header"]
|===
| Model | What it covers
| `models/html` | HTML elements, attributes, text and comments, with a generator that writes HTML text
| `models/html/bootstrap` | Bootstrap 5 semantics: documents with themes, containers, grids, and components for content, navigation, overlays and forms
| `models/typescript` | The declaration surface of TypeScript: packages, modules, declarations and type references, with a generator that writes sources and manages imports
| `models/react` | React components, hooks, contexts and JSX, on top of the TypeScript model
| `models/react/bootstrap`, `models/react/flow` | Bootstrap components in React, and React Flow diagrams with a simple layered layout
|===

The Bootstrap model describes semantics, not markup: a modal has a title, a size and whether it is centered and scrollable.
How that becomes elements, classes, ARIA and data attributes, and ids that Bootstrap's JavaScript connects, is the business of `BootstrapStructure`, used by the HTML generator for static pages and by the React generator for components.
One model of a page renders both ways.

Writing the page as a model has consequences beyond correctness.
The page model can be checked before it is written, by a test or an agent; it can carry markers that point back to the model elements each part was generated from (<<core-model>>); and it can be transformed, for example by adding a navigation panel to every page of a site after the pages were generated.

=== Navigation

Documentation sites of models need navigation that works for people, crawlers and agents alike.
The Bootstrap module's `NavigationTree` builds a side panel as nested `details` and `summary` elements, which work without JavaScript, so crawlers and agents read the tree as plain links.
Branches on the path to the current page are open, and the current item is marked with `+aria-current="page"+`.
For large models, a local tree renders the branches off the path as links without their children, so a page of a model with thousands of elements stays small.

=== TypeScript and React

The TypeScript model covers the declaration surface: packages, modules, interfaces, classes, functions, type aliases, and the type references between them.
Bodies are opaque code blocks, which carry references to the declarations they use.

Its generator writes sources to a volume of text (<<volumes>>) and owns import management, the hardest part of emitting TypeScript correctly: it walks the type references reachable from each module, resolves each to the module that declares it, computes the module specifier, decides whether an import can be `import type`, and aliases names that would collide.
The model is write-only by design; nothing in the runtime parses TypeScript.

The React model adds what the TypeScript model leaves opaque: components, hooks, contexts and JSX.
`ReactGenerator` writes JSX into `.tsx` modules compiled with the automatic runtime, or `createElement` calls into plain JavaScript modules that a browser runs as they are, without a build step.
HTML elements used in JSX are interpreted by the same structure the HTML generator uses, with attributes mapped to React props, so a page model and a component model mean the same markup.

Generating through models, not templates, keeps three things that templates lose:

* *Imports*, computed from references instead of maintained by hand.
* *Provenance*, from a source element through every intermediate model to the generated code.
* *Structure*: generated code that can be diffed, analyzed and reported on as a model, not compared as text.

=== What comes next

The generators are the building blocks of two things on the roadmap [.planned]#PLANNED#:

* *Documentation sites for models.* A site per model with a page per element, its documentation, its neighbors, provenance links and a diagram of its neighborhood, for any model built on the core model.
* *The reflective viewer.* A browser application that renders any model, and live telemetry, from the runtime's HTTP server, generated from models rather than written by hand. Meta's projection to TypeScript gives it runtime type information for dispatch (<<meta>>).
