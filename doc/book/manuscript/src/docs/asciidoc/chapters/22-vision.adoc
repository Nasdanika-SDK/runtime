[#vision]
== Roadmap and vision

The previous chapters describe what the runtime does in this edition.
This one describes where it is going: the North Star that orders the work, the picture that the pieces fit into, and the increments planned next.
Plans change as they meet code, and the runtime's site and repository are the current record; this chapter is the plan as of October 2026.

=== The North Star

The North Star is agentic work on models: executable graphs whose activities include AI agents, operating on bounded, typed models, with transactional safety and state saved to Git, runnable on a laptop, in a container or in a CI pipeline as the same artifact.

Each part of that sentence is a constraint:

* *Executable graphs.* Work is a graph of activities with transitions between them, drawn as a diagram and executed as it is drawn.
* *Activities include AI agents.* An agent is an activity like any other, with inputs, outputs, tools and a record of what it did.
* *Bounded, typed models.* Agents work on models with declared types and documented terms, not on unstructured text, so what they produce can be checked.
* *Transactional safety.* An agent's changes are a change set, reviewed before it is applied and reversible after.
* *State saved to Git.* History, review and rollback come from the tool every developer already has.
* *The same artifact everywhere.* No server to install and no platform to adopt: what runs on a laptop runs in a pipeline.

The minimum credible demonstration is one agentic workflow with Git-backed state and transactional rollback, runnable locally and in CI.
Everything in this book is on the way there, and useful before it.

The work is ordered by a rule: an increment is admitted when it states the agentic capability it adds, the demonstration that shows it, what it pulls into the runtime, and that it builds green from a clean clone.
Code that no increment needs does not move.

* *The data plane* is where data sits: files, repositories, a running JVM, a Maven repository, an issue tracker, a cloud's resource graph.
* *The semantic plane* is models loaded from the data, with references resolved across sources.
* *The presentation plane* is what people and agents read: Markdown, static HTML, JavaScript modules and React applications generated from models.

Reads flow up through volumes, which pull what is asked for.
Writes flow down through commands, the control plane, as recorded change sets and commits.

Layer by layer, a stack built this way has data source volumes that serve one resource each, a mount that composes them under paths (`jvm`, `maven`, `issues`), a resource set that resolves references across the mount, and representations chosen by the type of the source object and the requested view, whose output is again a volume: served over HTTP, mounted over WebDAV, or copied into a zip for static hosting.
A model object becomes a folder with a static page, an application page, its JSON and its JavaScript module.

=== Next: browsing and serving

[.planned]#PLANNED#

* *The reflective viewer.* A browser application over the JavaScript model, which is read-only facades over EMF JSON, with a property sheet per object, categories from the annotations Xcore models already carry, and custom views resolved by capability, with the class of the object as the requirement.
* *Telemetry and JVM browsing* in the viewer, the generic views first, and custom ones where they are visibly needed: spans want a timeline, not a property sheet.
* *Live telemetry in the browser.* A subscriber that builds the telemetry model from span events as they happen, exposed as a watchable volume, delivered to the browser with server-sent events, so a running command and a recorded one look the same.
* *`http`, `https` and `webdav` commands* over the handlers of <<serving>>, with safe defaults and token authentication.
* *The runtime's site*, with its modules and models, generated by the runtime.

=== Next: more volumes

[.planned]#PLANNED#

* *A JVM volume*: the JVM model of <<jvm>> served one module per resource, references as proxies resolved on demand.
* *An Azure volume* over the plain REST API, where resource ids are already paths and the resource graph reports changes.
* *A Git volume* that commits without a clone, over the GitHub and GitLab APIs, and an overlay that keeps writes in memory over a read-only base until they are committed.
* *A caching volume*, and a coalescing processor that folds queued changes into the net change per path.
* *Writes through change sets*: a client submits a recorded change set to a command inbox, the command side of a CQRS split, and raw bytes remain plain `PUT` and `DELETE`.

=== Next: the command line

[.planned]#PLANNED#

* *`nsdk install`*: extend an installation from Maven coordinates, with profiles for rollback, so new models and commands arrive without rebuilding the distribution.
* *Command lines as models*: a Groovy DSL for long command pipelines, and forms generated from command definitions, sub-commands as wizards and mix-ins as sections, with an assistant that proposes a command and a person who keeps or undoes it.
* *Diagrams and narrated video as models*: Draw.io, presentation and PowerPoint models as technology models, layout with ELK, rendering with React Flow, and a video model whose narration and screen events are regenerated as build artifacts.

=== The agentic increments

The increments toward the North Star, in their planned order [.planned]#PLANNED#:

[cols="1,3",options="header"]
|===
| Capability | Demonstration
| Conversations with tool calling, recorded as models | An agent loop against Anthropic and OpenAI models with file tools, view, create, replace, insert, glob and grep, over an in-memory volume: a seeded folder and a task in, a diff and a recorded session out
| A sandbox | The agent writes to an overlay over a read-only base; the changes are reviewed as a diff, then committed or discarded
| Model choice and portable sessions | A saved session is reloaded and continued with another provider, selected by requirement
| Declarative tools | Tools from a tool model, with input schemas generated from Meta, and the same tools over the Model Context Protocol from the runtime's own server
| Provenance | Every element an agent produced says which turn and which model produced it, in its markers
| Model and graph queries | XPath over models, then a read-only Cypher tool over the graph: the query side
| Reviewable writes | A command tool that takes changes, returns a plan, applies and records them: the command side
| Executable agentic graphs | A diagram's transitions as `Flow` publishers and subscribers, one workflow with one agentic activity running until it settles
| Git-backed state and rollback | Durable inboxes, one commit per settled step, a CI trigger, and a reply approved in a pull request, then replayed over the diagram from history
|===

The last two rest on one idea: a commit is a message.
Transitions of an executable graph are publishers and subscribers, and payloads are models that serialize to JSON.
When an activity sends an event, the event is committed; the commit triggers a pipeline that runs `nsdk`, which loads the graph, finds the event and delivers it to the receiving activity.
When the run settles, its changes are committed and pushed, which may trigger another run elsewhere.
Execution is recorded as commits, so it can be inspected, replayed over the diagram, and reverted.

The reactive file system of <<volumes>> is the runner: processors, deterministic or agentic, react to file changes until nothing changes, and one commit records the run.

=== Humans at both ends of the line

Draw software development as a line from intent to operation.
AI takes the middle, writing and testing code, and pushes people out to both ends.

To the left is intent: the big picture, the vocabulary, the specification.
Meta (<<meta>>) and the core model's documentation are tools for that end.

To the right is assurance: knowing what the system actually did.
Telemetry per unit of work saved as models (<<telemetry-model>>), snapshots of running systems (<<jvm>>), recorded changes in the spans that made them, and live observation (<<watching>>) are tools for that end.
The runtime is built for both ends of the line, and for the agents in the middle to be checked from both.

=== An architecture method on Git

The same pieces compose into a lightweight architecture method, in the spirit of TOGAF without its ceremony:

* *Git is the architecture repository*, with models in it, reviewed as pull requests.
* *Meta models the business concepts* and the data, the vocabulary everything else uses.
* *Diagrams model processes and application architecture*, as sources, not pictures, and processes may later be executed.
* *Technology stacks are managed as models*, with coordinates for variants by region, tier or audience.
* *Agents are grounded* in the models, code is generated from them, external systems are wired in through volumes, and snapshots are taken with a copy.

It is the answer to the question the first chapter asked: more structure, for less effort than the tools that make structure expensive.

=== The model tower

The runtime's models are the lower floors of a tower of small models, each extending the ones below instead of reinventing them: the core model, then Meta, the JVM model, telemetry and the file model.
Above them sit floors for work and roles, ownership and governance, accounting, kinds that configure, and occupancy, where elements are situated in coordinates such as time, jurisdiction and tier.
Each floor enters the runtime when an increment needs it.
