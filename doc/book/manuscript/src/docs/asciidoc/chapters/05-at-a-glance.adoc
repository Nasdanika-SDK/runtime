[#at-a-glance]
== The runtime at a glance

This chapter puts the whole runtime on a few pages: the modules and what each is for, the three planes they serve, how the pieces find each other, and what happens, step by step, when one command runs.
Later chapters zoom into each part; this one is the map you come back to.

=== The modules

The runtime is one Maven reactor in one Git repository, released as one unit with one calendar version.
<<module-map>> lists its modules; <<modules-reference>> has the full reference with every service each one provides.

Two things stand out.
`common` sits under almost everything, which is why it is held to the strictest rule about what it may depend on.
And most models do not depend on `common` at all: a model is EMF, and anything else is somebody else's concern.
The exceptions need something only the runtime has: volumes, for the file and TypeScript models; telemetry, for the exporters and for layout with ELK; `DerivedSubsetEList`, for the slides of a presentation; and the Draw.io API and capabilities, for the resource factories of the Draw.io and SVG models.

=== Three planes

It helps to sort what the runtime does into three planes, with two seams between them.

[#planes]
.Three planes and the volumes between them
[plantuml,planes,svg,pdfwidth=90%]
----
skinparam defaultFontName "Noto Sans"
skinparam defaultFontSize 11
skinparam rectangle {
  BackgroundColor #F2F7FA
  BorderColor #1B8EC6
}
skinparam ArrowColor #0F4C6E

rectangle "Presentation plane\nHTML, Bootstrap, React, Markdown, text" as presentation
rectangle "Semantic plane\nmodels in a resource set, cross-references resolved" as semantic
rectangle "Data plane\nfiles, a running JVM, Git, Jira, Maven, cloud APIs" as data
rectangle "Control plane\ncommands, telemetry, change recording" as control

data -up-> semantic : volumes, loaders
semantic -up-> presentation : representations
control .right.> semantic : writes
control .right.> presentation : serves
----

The *data plane* is raw data where it lives: files on disk, a running JVM, a Git repository, Jira, a Maven repository, a cloud provider's API.
The *semantic plane* is models loaded from that data, typed, with cross-references resolved, in a resource set.
The *presentation plane* is how people and programs see the models: HTML pages, a React UI, Markdown for an agent, plain text for a console.

Reads flow up.
A volume presents data as files, and EMF loads resources from those files through a URI handler; or a loader reads an API and builds a model directly.
A representation turns model objects into pages or files, and another volume presents those for serving, copying or mounting.
Writes flow down, through commands, with telemetry and change recording on the way.

The planes explain why the runtime has volumes at all.
A volume is the seam between the data plane and the semantic plane, and again between the semantic plane and channels such as HTTP, WebDAV or a directory.
The same five-method interface serves both seams (<<volumes>>).

==== An example

This example is partly built.
The https://jira.models.nasdanika.org/[Jira model] exists, and I have used it to snapshot Jira and give the snapshots to an AI assistant, but that was before the volume module existed.
A Jira volume does not exist yet; it will be built on demand, and should be straightforward.

Take a Jira story, and suppose a Jira volume presents it at `jira/MYPROJECT/issues/ISSUE-123/index.json` as JSON, and at `index.xmi` next to it as XMI.
Neither file is stored anywhere: reading either one makes a REST call to Jira and materializes the issue in that format.
Related objects, such as the project, its components, users and linked issues, are relative URI references, and EMF loads their resources on demand, when a reference is followed.

Because Jira is a volume, its content can be copied to a directory or a zip archive like any other files.
Take a snapshot today and another in a month, load both, and compare them with EMF Compare to see what has changed.

Because the issue is an EMF object in the semantic plane, it can reference semantic elements that did not come from Jira: a Git commit, a file on disk, or an object from any other system that is also loaded as a model.

Going up, the same issue has representations in different formats: an HTML page, a Markdown or AsciiDoc document, a diagram, or any other format the presentation plane supports.
Those representations reach people and agents over different channels: a web browser, a file system mounted over WebDAV, or a directory they are copied to.
For example, copy the AsciiDoc representations to a directory, then generate a PDF from them or give them to an AI assistant for analysis or enrichment.
AsciiDoc carries more structure than plain text or Markdown, such as document attributes, cross-references and typed blocks, and it might be better suited to AI-assisted analysis and enrichment.

==== Who the planes are for

The planes say where things are, but not why the presentation plane has so many formats: HTML and Markdown, SVG and Draw.io, a PDF and a JSON file.
The answer is a vocabulary older than the runtime, from ISO/IEC/IEEE 42010 and TOGAF, which the Nasdanika enterprise model puts in one diagram.
<<stakeholders>> is a lighter version of it.

A *stakeholder* is anyone with an interest in a system: a business owner, a risk officer, an engineer, and also an agent or a program.
Stakeholders have *concerns*, the things they need to know or decide.
A *view* addresses concerns.
It is made of *representations*, such as a section, a table or a diagram, and a representation *represents* elements of the semantic plane: objects in the models of several semantic domains, many Ecore models in one resource set.
A view sent to stakeholders is a *message*, delivered over *channels*: a directory, HTTP, WebDAV, MCP, a printed book.
One view goes over many channels, and a channel carries many views.

Formats sit between representations and channels.
A representation is available in several formats: a table as Markdown, AsciiDoc or HTML, a diagram as SVG or Draw.io.
A channel accepts some formats and not others: a browser takes HTML, an agent takes Markdown, a printer takes PDF.
A human stakeholder who wants a table gets it as HTML in a browser or in a PDF; an agent gets the same table as Markdown.

The enterprise model defines an enterprise as a group of stakeholders and resources devoted to a mission (<<more-structure>>).
Views exchanged as messages are how the mission is pursued, which gives two measures: effectiveness, whether a view addresses the concern it is for, and efficiency, what it costs to produce, deliver and understand.
Formats are about efficiency.
That is why the runtime has a format for every reader.
SVG is for people reading a page or a book: it is static, embeddable and needs no viewer.
Draw.io is for people who edit, because the picture is also its source.
Markdown, or the model itself, is for agents.
Each format serves some stakeholder over some channel.

The vocabulary also says what a document is: a view whose sections are representations.
A document generated from a model and a document written by hand are the same kind of thing, and a Markdown file loaded as a model is a view that can be rendered again, in another format, for another stakeholder.
And it describes the polymorphic UI (<<polymorphic-ui>>) from the outside: given a viewpoint, which names the concerns to address and the representations that address them, a format and a channel, it builds a view.
Viewpoints and stakeholders can be kept in catalogs, like any other model: a Sankey chart for "where does the money go", a property table for "who owns what"; business, risk and technology stakeholders.

It is also the first model an effort needs.
A project charter names the stakeholders, a communications plan says what each of them receives and how, and a quality management system, such as the one Article 17 of the EU AI Act requires, covers communication with authorities, customers and other interested parties.

The runtime's design follows this vocabulary, but the enterprise model is not part of the runtime yet.
It is [.planned]#PLANNED# as a nano-model of the core module (<<core-model>>), so that stakeholders, concerns, formats and channels become types, and a view can be asked for by them.
It is introduced here because it explains much of what follows.

=== How the pieces find each other

Nothing in the runtime is wired by hand, and nothing is configured in XML or YAML.
Four mechanisms, from the simplest to the most capable, connect the parts.

*Java services.*
A module declares in `module-info.java` that it provides an implementation of a service interface, and `java.util.ServiceLoader` finds every provider on the module path.
Resource set configuration uses services: EPackages, URI handlers, adapter factories and `ResourceSetContributor`s (<<models>>).
So does the capability framework itself, to find capability factories.

*Capabilities.*
A capability factory is a service that interprets requirements.
A requirement is a type, possibly generic, with optional payloads: "a `Function<Library, String>` for the markdown format".
Factories may raise their own requirements while satisfying one, and the loader resolves the whole graph, once per requirement, with cycle detection (<<capabilities>>).

*Adaptation.*
An object can declare, with annotated fields and methods, what it can be adapted to, by generic type and with optional context.
Adaptation answers "can this thing give me what I need?" without either side knowing the other's class (<<generic-types>>).

*Wiring.*
A command declares, by generic type, what it needs from its parent and which sub-commands it takes.
Commands contributed as capabilities are matched to parents by those declarations, and the parent is adapted to what the child needs just before it runs (<<wiring>>).

Each mechanism builds on the previous ones.
Commands are capabilities; capability factories are services; wiring is adaptation.

=== One command, end to end

To see the parts work together, follow one command through a distribution: `nsdk library save shelf.xmi`, which saves the library the `library` command supplies to a file.
<<one-command>> shows the main steps.

[#one-command]
.One command, end to end
[plantuml,one-command,svg,pdfwidth=72%]
----
skinparam defaultFontName "Noto Sans"
skinparam defaultFontSize 12
skinparam ArrowColor #0F4C6E

  BorderColor #1B8EC6

  BackgroundColor #FFFFFF
  BorderColor #A9C7D8
}
start
:Launcher builds a unit of work:\none OpenTelemetry SDK with model exporters;
note right: continues TRACEPARENT if set
:Capability loader assembles the command tree;
note right: contributed commands, parents\nmatched by generic type
:picocli parses the arguments;
:Wiring injects parents, root to leaf;
note right: save gets a supplier from library
:The save command executes in its span;
:The supplier loads the library\nin the span of save;
:Resource set configured and resource\nsaved, in spans, with progress logs;
:SDK closes: traces, logs and metrics\nsaved as models;
stop
----

. *The launcher builds a unit of work.*
It creates a directory for this launch's telemetry, builds an OpenTelemetry SDK whose exporters write traces, logs and metrics as models, and makes it current.
If a `TRACEPARENT` environment variable is set, by a CI step for example, the launch continues that trace.
Everything that follows reports to this instance and to no other (<<distributions>>).

. *The capability loader assembles the command tree.*
It asks for root commands; the root command's factory produces `nsdk`, and every command factory on the module path is asked whether its command fits under `nsdk`, then under each command added so far.
The `library` command fits under `nsdk` because it declares the root command as its parent.
The runtime's `save` command fits under `library` because it declares that its parent must supply a collection of EMF objects, and `library` declares an adapter that does (<<commands>>).
Each command arrives with its own sub-commands and mix-ins attached, so what the loader returns is the whole tree.

. *picocli parses the arguments* against that tree and finds `nsdk library save` with one positional parameter.

. *Wiring injects parents.*
After parsing, from the root to the executed command, each command's `@Parent` members are filled by adapting its parent.
`save` receives a supplier from `library`; nothing is loaded yet (<<wiring>>).

. *The command executes in its own span.*
`save` calls the supplier, which loads or builds the library inside `save`'s span, so the cost is attributed to the command that needed it.
It creates a resource set, which is configured from services in a span with a log record per contribution, and saves the resource in a span with the byte count, while the URI handler logs progress for large streams (<<telemetry>>).

. *The unit of work ends.*
Closing the SDK exports what is pending, and the exporters save `traces.yml`, `logs.yml` and `metrics.yml` in the launch's telemetry directory, with log records nested in the spans they were emitted in (<<telemetry-model>>).

Nothing in that sequence was configured.
The commands are present because their modules are on the module path, the wiring follows from their declared types, and the telemetry is there because the runtime's code reports through the OpenTelemetry API to whatever instance is current.

Each model module keeps its Xcore source under `src/main/resources`, its generated Java under `src-gen` (committed, so that editors without Maven integration see it), and its hand-written code under `src/main/java`.
