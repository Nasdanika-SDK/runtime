[#more-structure]
== More structure with less effort

Glass is a curious material.
It is a solid, it holds its shape, and you can build with it.
Look closely, though, and there is no crystal inside: the atoms have short-range order, each one sitting sensibly next to its neighbors, and no long-range structure at all.
It is a liquid that stopped moving before it got organized.

Most enterprise knowledge is glass.
Every team has its documents, its diagrams, its spreadsheets and its wiki pages, and each of them makes sense locally.
Step back and there is no structure that connects them.
The definition of a customer lives in a database schema, a JSON Schema, a partner's XML Schema, a Java class, a Confluence table and three spreadsheets, and nothing relates them.
Each is a projection of a model that nobody ever wrote down.

This chapter is about why that happens, what changed recently that makes it fixable, what kind of structure lasts, and what the Nasdanika SDK Runtime is in that picture.

=== Structure has been expensive

We are managing twenty-first century complexity with twentieth century tools.
Office documents were designed to be printed.
Wikis were designed to be edited by anyone, which is exactly why nobody owns what they say.
Drawing tools produce pictures: a box on a diagram looks like a system, and nothing about it says which system, who owns it, or whether it still exists.

None of this is news, and the industry has tried to fix it more than once.
I learned UML in the 1990s, when it was going to be how software was designed.
By the 2010s I had concluded that it was dead in the enterprise, and I was not alone.
Simon Brown observed in the C4 model book that many teams "have already thrown them out in favour of much simpler 'boxes and lines' diagrams".
The reason was not that structure is useless.
The reason was cost.

Modeling came with a tax.
The tools were desktop applications with their own repositories, their own licenses and their own learning curves.
The open source alternative, the Eclipse Modeling Framework, was excellent and lived inside an IDE: to use a model you installed Eclipse, configured a workspace and generated code with a wizard.
Catalogs and ontology platforms moved the tax to a server you rent, with an administrator who owns the whole graph.
Every one of these asks people to adopt something before they get anything back.

So people rationally chose less structure.
When a model costs more to keep than it pays, a spreadsheet wins, and the spreadsheet is the real competitor of every modeling tool.
It is free, everybody can use it, and it never asks anyone to adopt anything.

The price of that choice is paid later, and by somebody else.
Ask three people what the third measure on a list in some system prompt means and you get three answers.
Ask who owns the definition and you get silence, then a suggestion that some other team may know.
The knowledge exists. It lives in people's heads, and it leaves when they do.

=== What changed

Four things changed, and together they make structure cheap enough to keep.

*The JDK grew up.*
Virtual threads became final in Java 21, so blocking code no longer costs a platform thread, and the main reason for reactive libraries disappeared.
`java.util.concurrent.Flow` has been in the JDK since Java 9, the HTTP client since 11, `ScopedValue` since 25, and a class file API since 24.
Many of the libraries an enterprise application drags along were written before the JDK had the feature.
The reasons to take those dependencies expired; the dependencies did not.
A runtime that starts today can say "if the JDK can do it, use the JDK" and mean it.

*EMF works without Eclipse.*
EMF itself never needed the IDE; the tooling around it did.
Today a model is a text file in Xcore, generated by a Maven plugin in any build, edited in any editor, and checked into Git next to the code.
The twenty years of engineering in EMF (reflection, serialization, notifications, change recording, cross-resource references) come without the workspace.

*OpenTelemetry standardized signals.*
Spans, log records and metrics have one API, independent of where they end up.
Code can be instrumented once, and whether the signals go to an operational backend, to a console, or into a model that is kept forever is decided by whoever runs it.

*A new coworker arrived.*
AI assistants are capable, and they see only what they are given: meeting notes, wiki pages, a deck from three years ago.
They cannot absorb tribal knowledge at the coffee machine.
An assistant grounded in a declared, versioned, owned model answers from it and can cite it; an assistant given a database schema and a wiki export infers, and inference is not a chain of custody.
At the same time, assistants are good at the mechanical part of modeling: they draft a model from a description, a human corrects it, and correcting is much cheaper than authoring.

There is an old camping joke about two friends who meet a bear.
One of them starts lacing up his running shoes. "You cannot outrun a bear!" "I do not have to outrun the bear. I only have to outrun you."
Businesses do not have to outrun AI either.
They have to harness it: ground it in their own terms, systems and rules, so that people and assistants speak the same language.
The harness is structure.

=== Small, formal, composable

Cheap structure is necessary but not sufficient: structure also has to last.
It lasts when it has the three properties that keep code and its libraries alive while the documents around them rot: it is small, formal and composable.
Take away any one of them and the failure is familiar.
Small and formal but not composable is the monolithic repository of an enterprise architecture tool.
Small and composable but not formal is the wiki that drifts the day it is written.
Formal and composable but not small is the canonical enterprise data model that nobody updates.

The runtime is built to make all three cheap.
Micro-models keep structure small (<<principles>>), Xcore keeps it formal (<<models>>), and models that reference each other across repositories, with capabilities and commands that find each other by type, keep it composable (<<capabilities>>, <<wiring>>).

=== What the runtime is

The Nasdanika SDK Runtime is the set of modules everything else in the Nasdanika SDK runs on, in one repository, released as one unit.
The analogy I use is the Java runtime, `rt.jar` and its successor, the JDK's module image, or the runtime of an integration platform: the part you install first and build on.

It is built on three things, which I call the "pure Nasdanika" foundation: the JDK, EMF core and the OpenTelemetry API.
All three are small, stable and standard, and any module may assume them.
Anything beyond them has to justify itself.

On that foundation the runtime provides:

* *Models as the API.* Data and operations are defined in Xcore, generated by Maven, and handled by EMF: typed, documented, serializable to XMI, JSON, YAML and binary, and reflectively invocable, so an operation is also a tool a command line or an agent can call (<<models>>).
* *A capability framework* that finds what a piece of code needs by requirement, including full generic types, so `Supplier<Library>` and `Supplier<Catalog>` are different things to ask for (<<capabilities>>).
* *Telemetry as part of the code.* The runtime's own operations create spans and log records through the OpenTelemetry API, one OpenTelemetry instance per unit of work, and you can watch them live without an SDK or save them as a model next to the models they changed (<<telemetry>>).
* *Volumes*, a small file abstraction in the shape of Go's `io/fs`, so that a model, a running JVM or a remote system can be presented as files, loaded by EMF, served over HTTP or mounted as a drive over WebDAV (<<volumes>>).
* *A command line assembled from contributions.* Commands are capabilities contributed by modules and wired to their parents by generic type, so adding a dependency adds commands (<<commands>>).
* *Models that ship with it*: a core model for identity, documentation and provenance, Meta as a language-neutral type system, a JVM model, a telemetry model, and models of HTML, Bootstrap, TypeScript and React that make the web a generation target (<<models-in-the-runtime>>).

=== What it is not

It is easier to place something by what it refuses to be.

*Not Eclipse.* There is no workspace, no plug-in registry, no update site, no OSGi. Modules are JPMS modules and Maven artifacts. The influence of EMF is everywhere; the IDE is nowhere.

*Not Spring.* There is no container that owns object lifecycles, no classpath scanning, no XML or annotation configuration of beans. Services are registered in `module-info.java`, and capabilities are resolved on request.

*Not a modeling tool.* There is no diagram editor in the runtime. Models are authored as text (Xcore, a Groovy DSL, YAML), harvested from what already exists, or drawn in tools people already use, and the runtime loads them.

*Not an observability backend.* It does not compete with Grafana or Datadog. Operational telemetry is sampled, retained for days and forgotten; the runtime is for the small fraction of signals worth keeping, resolved against a model, for years.

*Not a platform you rent.* There is no server. Models live in Git and in Maven repositories, reference each other by URI, and are owned by whoever publishes them. Everything runs locally, in a container, or in a CI pipeline, as the same artifact.

*Not all or nothing.* You take the modules you need. A Java program that wants a volume over a directory depends on the `volume` module and nothing else above the foundation.

=== Who gets what

*Architects* get structure at the cost of a text file.
A vocabulary in Meta is one source for a generated glossary, a JSON Schema for a tool call, a TypeScript package for a user interface, and a lookup an agent can be grounded in (<<meta>>).
A running system can describe itself: a JVM snapshot shows what an assembly became after its modules were resolved, which no build file says (<<jvm>>).
Telemetry kept as a model is evidence of who changed what, in the course of what work, years after the fact (<<telemetry-model>>).
Because models are files in Git and artifacts in Maven repositories, teams own their parts and reference each other's, and nobody administers the whole.

*Developers* get a foundation that is small, observable from the first line, and tested.
The examples in this book depend on the runtime and on JUnit; the runtime depends on the JDK, EMF, the OpenTelemetry API and a handful of libraries that do something the JDK does not.

*Agents* get typed models instead of prose, operations that are tools by construction, and file systems they already know how to use.

=== A short tour

The rest of the book explains how each piece works.
Here is what a few of them look like from the outside, using the output of the book's examples.

The first program in <<getting-started>> builds a one-class metamodel at run time, saves an instance as XMI, JSON and YAML, and does nothing else.
Run under a publishing OpenTelemetry instance, with no SDK and no backend, this is what it prints:

[source,text]
----
> Save a book
  > ResourceSetContributor.configure
    Contributed uri-handler ...ClassPathURIHandlerFactory$1
    Contributed contributor ...XMIResourceFactoryContributor
    Contributed contributor ...JsonResourceFactoryContributor
    ...
  < ResourceSetContributor.configure
  > Resource.save
    Saved file:/tmp/watch-it/book.xmi: 230 bytes
  < Resource.save
  ...
< Save a book
----

Nobody instrumented that program.
The runtime's resource set configuration, resource factories and URI handlers report what they do through the OpenTelemetry API, and whoever runs the program decides where it goes.

The command line example in <<commands>> contributes a `library` command and a few sub-commands.
The runtime's own `save` command was written long before that example and knows nothing about libraries, yet it appears under `library`, because the library command offers what `save` declares it needs: something that supplies a collection of EMF objects.

[source,text]
----
nsdk
  launcher
  hello
  library
    books
    export
      csv
      markdown
    save
----

And the recording example in <<telemetry-model>> edits a library inside a span, with the OpenTelemetry SDK exporting to the telemetry model.
Reading the saved traces back as a model, the change is in the span that made it:

[source,text]
----
Curate the shelf
  * created Library 'A Modeler's Shelf'
  Resource.save (2059 bytes)
  Correct the year
    * Book 'Domain-Driven Design'.year = 2004
    Resource.save (2059 bytes)
----

That last output is the point of the whole runtime in miniature.
"Somebody changed the year of a book" is a log line.
"In the course of the work named 'Correct the year', this attribute of this object changed to this value", with the work, the object and the attribute all being model elements you can navigate and query, is structure.
It cost one line of code: `Changes.record(...)` around the edit.

=== Where this is going

The runtime is a seed.
Its North Star, explained in <<vision>>, is agentic work on models: executable graphs whose activities include AI agents, operating on bounded, typed models, with transactional safety and state saved to Git, runnable on a laptop, in a container or in a CI pipeline as the same artifact.
Several capabilities on the way there are useful long before it, and they are what this book is mostly about: models without an IDE, telemetry without a backend, files without a file system, and a command line without configuration.

The next chapter states the principles the runtime follows.
They are short, and every later design decision traces back to one of them.
