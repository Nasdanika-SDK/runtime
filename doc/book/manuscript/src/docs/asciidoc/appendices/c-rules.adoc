== Rules of thumb for people and assistants

This appendix collects the rules the chapters explain, as short imperatives.
It is written to be pasted into the instructions of a coding assistant working on a Nasdanika project, and to be read by the people who review its work.
Each rule names the chapter that explains it.

=== Foundations

. Depend on the JDK, EMF core and the OpenTelemetry API, and nothing else, in code meant to be reused. Anything that needs more goes into its own module (<<principles>>).
. Use the JDK where it can do the job: `java.util.concurrent.Flow`, not Reactor; the JDK HTTP client and server; virtual threads; the service loader (<<principles>>).
. Derive identities from the module's path: the Java module `org.nasdanika.sdk.runtime.<path>`, dropping a trailing `model`, and the nsURI `+https://runtime.sdk.nasdanika.org/<path>+` (<<principles>>).
. Register by declaring: `provides` in `module-info.java`, never registration code (<<principles>>).
. Register by type with Java services, such as EPackages and resource set contributors. Use capabilities only for lookups that have a requirement object (<<principles>>, <<capabilities>>).
. Say what is stuck. A failure names what it needed, what it found and what was waiting for what (<<principles>>).

=== Models

. Write metamodels in Xcore. Give the GenModel's `modelDirectory` the Maven module's directory as its first segment (<<models>>).
. Contribute each package through an EPackage provider in the module's `services` package, declared in `module-info.java` (<<models>>).
. Create resource sets with `NasdanikaResourceSet.createAndConfigure()`, so that every contributed package, factory and handler is there and every load and save is traced (<<models>>).
. Choose the format with the extension: `xmi` to interchange, `yml` and `json` to read and review, `ebin` and `egz` for size (<<models>>).
. Extend the core model's `NamedElement`, or `ModelElement` for elements without names, and get identity, documentation and provenance with it (<<core-model>>).
. Prefer `getReferrers` to an opposite reference when the inverse is not part of the model's meaning (<<core-model>>).
. Fill markers. A loader, an importer and an agent record where an element came from (<<core-model>>).
. Keep a vocabulary in Meta when it has to be projected to more than one language (<<meta>>).
. Give a model a module of its own, a micro-model, only for a dependency the others do not want, a different set of consumers or a different maturity; otherwise add a nano-model, an `.xcore` file, to the module it changes with (<<principles>>).
. Keep the core concepts of a model on one diagram that a newcomer understands in a quarter of an hour. A model that needs two diagrams is two models (<<principles>>).
. Anchor long documentation to the element it describes, a page per element with `docRef`: a micro-wiki (<<core-model>>).

=== Types, flows and capabilities

. Ask with wildcards, `? extends`, at every level that is only read from (<<generic-types>>, <<wiring>>).
. Use ground types in requirements: classes, or parameterized types whose arguments are classes or wildcards (<<capabilities>>).
. Remember that objects carry no type arguments: what matches is always what was declared, a return type or a generic supertype (<<generic-types>>).
. Drive asynchronous work that must be ordered and settled with a `Pump` (<<flows>>).
. Emit only complete results from a capability factory: attach what a result needs before emitting it, so that a blocking load returns it whole (<<capabilities>>, <<commands>>).
. Do not return null from a `first` mapping to skip a source; distinguish sources by type, or use `all` (<<flows>>).
. Explain a resolution with a listener before guessing why a capability is missing (<<capabilities>>).

=== Telemetry

. Create one OpenTelemetry instance per unit of work and make it current. Never use `GlobalOpenTelemetry` (<<telemetry>>).
. Depend on the OpenTelemetry API in instrumented code; only the assembly that runs a unit of work depends on the SDK (<<telemetry>>, <<telemetry-model>>).
. Make an operation a span named `Type.operation`, and emit log records with the Logs API inside it. Do not use span events (<<telemetry>>).
. Put locations and identities in attributes: URIs, lines, names of types. Never put loaded values or credentials there (<<telemetry>>, <<groovy-dsl>>).
. Report progress with progress log records, at most once a second (<<telemetry>>).
. Carry the context across threads; the pump does it for its subscribers (<<telemetry>>).
. Record changes to models with `Changes.record` inside the span that makes them, so the change lands in the span (<<telemetry-model>>).
. Keep the telemetry of units of work worth keeping, as models, next to what they describe (<<telemetry-model>>).

=== Files and serving

. Use string paths, slash-separated and relative to the root, and keep URIs at the edges (<<volumes>>).
. Report hashes in entries when they are cheap to know (<<volumes>>).
. Push content with `writeTo` when you can; pull with `openStream` only when an input stream is required (<<volumes>>).
. Produce generated content with `Content.ofWriter`, so it is written when read, into the reader's stream (<<volumes>>).
. Ask a volume for capabilities instead of assuming them (<<volumes>>).
. Keep model URIs independent of where the bytes are: map them to volumes with `VolumeURIHandler` (<<volumes>>).
. Bind servers to the loopback address unless authentication is in front of them (<<serving>>).

=== Commands

. Extend `CommandBase` and implement `execute(span, logger, meter)`; write output to `spec.commandLine().getOut()` (<<commands>>).
. Contribute a command with a factory and `provides CapabilityFactory`, and open the command's package (<<commands>>).
. Declare what a command needs from its parent with `@Parent` and a generic type, and what it accepts with `@SubCommand` (<<wiring>>).
. Ask for an `ExecutionSupplier` for anything expensive, so the work happens in the command's span and only if it runs (<<wiring>>).
. Offer with `@Adapter` what any child may use; hand down with plain methods what only children written for the parent should use (<<wiring>>).
. Never let help fail. Wiring is skipped for help; keep constructors and option defaults free of work (<<wiring>>).

=== User interfaces

. Build pages and components as models of HTML, Bootstrap and React, and let generators write the text (<<web>>).
. Deliver applications as static files where you can, and serve the same bytes for previews and live data (<<web>>).
. Resolve the view of an element by its class, nearest first along its lineage, with a reflective view of last resort (<<polymorphic-ui>>).
. Ask for the view of an exact class at each level; do not leave the choice between views to the order of capabilities (<<polymorphic-ui>>).
. Write the general view once, and specific views only where they earn their place (<<polymorphic-ui>>).

=== The Groovy DSL

. Set a negative number with `upperBound = -1` or `upperBound(-1)`, never `upperBound -1` (<<groovy-dsl>>).
. Reference forward with paths; they are resolved after the script has run (<<groovy-dsl>>).
. Prefix a path with `./` when a local name clashes with a class name (<<groovy-dsl>>).

=== Working with an assistant

. Record the binding of decisions: what was decided, by whom or by what, in the course of what work, and on what evidence, at design time and at run time (<<built-with-ai>>).
. Ask whether a task should exist before asking an assistant to do it faster (<<against-the-grain>>).
. Keep ownership with the people who will live with the result: they choose the language and the stack, and they review what an assistant binds (<<against-the-grain>>).
. Measure a system by what it does, not by its lines of code, services or boxes on a diagram (<<against-the-grain>>).

=== For assistants

. Ground answers in models and their documentation, and cite elements by their URIs.
. Check an API against the module reference (<<modules-reference>>) and the listings of this book and of the Zephyr Books, which compile and are tested, before using it. Do not invent methods.
. Go to a module's Nasdanika Zephyr Book for what this book only outlines, and to the module's test sources for the complete code behind a listing (<<zephyr-books>>).
. Respect the status labels. Present [.sketch]#SKETCH# and [.planned]#PLANNED# features as designs, never as available.
. Propose changes as recorded change sets or diffs that a person reviews; do not apply them silently.
. Say which decisions you bound and why, so that the people who own the result can review them (<<built-with-ai>>).
. Write original prose when documenting the JDK and other licensed specifications; never reproduce their text (<<jvm>>).
. Prefer the surfaces the runtime gives you, commands and files, to new integrations.
. When you learn something about a model element, write it into the element's documentation page, its micro-wiki stub, so the next person or assistant finds it there (<<core-model>>).
. Spend effort at the right altitude: change the model or the generator rather than the code it generates (<<built-with-ai>>).
