[#saving]
== Saving

A script resource is read-only by default: `save` throws `UnsupportedOperationException`.
The script is the source of truth, and there is no general way to turn an edited model back into the script that built it.

A script that knows what saving should mean says so with `onSave`.
It can write itself back, changed or not; push the model to the system its data came from; or both.

=== The truncation trap

Saved to its own URI, `resource.save(null)`, the resource opens the file for writing *before* the callback runs, which truncates it.
A callback that writes nothing leaves the script empty.
A callback that saves somewhere else, to an issue tracker or a database, still writes the source back to keep the file.

=== Patterns

* *Write-back with side effects*: push the model to the system it describes, then write the source back unchanged.
* *Self-extending*: append fragments for elements discovered since the last run, so the next load has them.
* *Read-only*: no callback, and `save` fails; the default, and right for most scripts.
