[#capabilities]
== Capabilities

Adaptation asks an object you already have.
Capabilities answer the question that comes before it: where do the objects come from?

A *requirement* says what is needed.
A *capability factory* says which requirements it can handle and creates *capability providers* for them, which publish the capabilities.
A *capability loader* takes a requirement, asks every factory, and collects what they provide.
Factories can have requirements of their own, which the loader resolves within the same resolution.

With a type and no payload, a requirement is a lookup by type: what `ServiceLoader` does, but generic, lazy, asynchronous, and able to resolve dependencies.

=== Factories from methods

Most factories are not written by hand.
A `ReflectiveCapabilityFactory` is assembled from methods annotated with `@Capability`, so one class, and one `provides` entry, contributes many capabilities:

<3> Parameters of the requirement's payload, here a `String`, in order; and injected parameters, here the `Loader`, by type.
<4> A dependency, resolved within the same resolution. `CompletionStage` delivers the capability when it is ready.

.Requirements by type and by payload
[source,java]
----
include::{booktests}/CapabilityTests.java[tag=reflective-test,indent=0]
----
<1> A requirement can be a bare type. Only `books()` provides a `Supplier<Book>`.
<2> A wildcard admits both suppliers.
<3> A requirement with a payload: a `Catalog`, for the branch "Downtown". `catalog` takes a `String`, so it matches; the other methods take no payload, so they do not.

What a method takes:

* *Injected parameters*, by type, in any position: `Loader` for dependencies, `Span` (the method's own span), `Logger`, `Meter`, `OpenTelemetry`, and `Type`, the required type, for a method that serves a range of them.
* *Payload parameters*, every other parameter, matched to the requirement's payloads in order: as many parameters as payloads, each payload an instance of its parameter's class, or null for one that is not primitive.

What a method returns:

* *The capability*, matched by its declared type.
* *A way of delivering it*: `CompletionStage<X>`, `Flow.Publisher<X>`, `CapabilityProvider<X>` or `Flow.Publisher<CapabilityProvider<X>>`. These are always unwrapped, and `X` is matched.
* *A container*: `X[]` or an `Iterable<X>`. The declared type is matched first, so a requirement for `List<X>` gets the list; only if it does not match are the elements, so a requirement for `X` gets them one by one.

Null provides nothing, which is how a method declines.
A generic method, `<T> Supplier<T> make(Class<T> type)`, and a `void` method are refused when the factory is created, because their declarations say nothing that can be matched.

=== Composition

Loaders compose:

* `CapabilityLoader.concat(loaders...)` lets every loader contribute, in order.
* `CapabilityLoader.fallback(loaders...)` stops at the first loader that provides anything.
* `CapabilityLoader.cached(loader)` remembers answers across calls, which a loader does not do by itself. Opt in where the same requirements recur and the answers are stable.

Composed loaders keep their resolutions separate.
To let factories from several places satisfy each other's dependencies, compose their *sources* instead:

.A local source in front of a global one
[source,java]
----
include::{booktests}/CapabilityTests.java[tag=composition,indent=0]
----

The library capabilities in the local source find the credentials in the global one.
`CapabilityFactorySource.serviceLoader()` is the global source in an application, and a local one in front of it overrides or adds capabilities for one task.

A loader is stateless and not closeable: the memory of a resolution lasts as long as the resolution, and disposing of factories is the business of their source.
That is what makes the shared instance safe to share.
