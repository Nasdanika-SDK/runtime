[#adaptation]
== Adaptation

Matching types answers "does this declaration fit that one".
Adaptation answers a question objects are asked all the time in a program assembled from parts: "can you give me what I need?"
The asker has an object and a type; the object answers with something of that type, or with null.

The idea is old.
Eclipse's `IAdaptable` and EMF's adapter factories ask it with a class.
This module asks it with a type, and lets objects answer through declarations instead of code.

A method matches when it has as many parameters as there are context values, and each value is an instance of its parameter's class, boxed for primitives, or null for a parameter that is not primitive.

=== The rules

In order:

* With no context, the object itself is returned if its own declared type matches.
* Otherwise, adapter fields and adapter methods without parameters are tried; with context, adapter methods whose parameters accept the context.
* Of the candidates whose declared type is assignable to the requested one, the more specific are tried first, then fields before methods, then by name. The first non-null value wins.

Members are found once per class and remembered, so the cost of reflection is paid once.

ifdef::editor-notes[]
[IMPORTANT,caption="Editor's note"]
====
"More specific first" is computed by `Types.specificity`, which counts the supertypes of the *erased* type. `Supplier<Book>` and `Supplier<Publication>` both erase to `Supplier`, so they tie, and the member name decides. A request for `Supplier<? extends Publication>` gets `books` because "books" sorts before "publications", not because it is more specific; the test `AdaptationTests.specificity` passes for that reason. The same ordering is used by `ReflectiveCapabilityFactory` and by command wiring. A fix: break ties between members whose erased types are equal by comparing their declared types with `Types.isAssignable`, so that a member assignable to the other comes first.
====
endif::[]

<2> A `Box` created with a diamond carries no type arguments, because instances do not; for it, `T` is only its bound, `Object`, and an `Object` is not a `Book`.

The second line is the rule of <<type-not-class>> at work: declarations, never instances.
To adapt by a type argument, fix it in a class.

Overrides of adapter methods stay adapters, without repeating the annotation, and the override is what is called.
