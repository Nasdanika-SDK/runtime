== Models in volumes

`VolumeURIHandler` bridges EMF onto a volume: URIs below a base URI are paths in the volume, so a resource set loads and saves resources through the volume's reads and writes.
The model of this chapter is an Ecore package with a class per term of the glossary, so that the book needs no model of its own; any EMF model is stored the same way.

=== How URIs map to paths

* The URI `<base>a/b%20c.xmi` is the path `a/b c.xmi`: the part below the base, split into segments, each decoded. The base itself is the root.
* A query and a fragment are ignored, so the URI of an object maps to the path of its resource.
* URIs whose decoded path has empty, `.` or `..` segments, or an encoded slash, are not handled.
* A base without a trailing separator gets one, so `glossary://models` and `glossary://models/` are the same base.

=== What the handler does

* *Reading* opens the path's content. A missing path is a `NoSuchFileException`.
* *Writing* needs the `Writable` capability, and is otherwise refused as read-only.
* *Attributes* come from `stat`: the time stamp, the length, whether a path is a directory, whether it is read-only, which it is without the `Writable` capability, and the hash, as the attribute `hash`. Setting attributes is ignored, as by EMF's default handler.

The model never mentions where it is stored.
Moving models from a working tree to an in-memory volume, a Git overlay, or a volume over a remote system changes one handler, not the models and not the references between them.
